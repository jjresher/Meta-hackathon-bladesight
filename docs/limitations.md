# Known limitations

What does not work or is not covered, its impact, and the issue that owns it. Shown honestly in
the README and the Evaluation page. See skill `write-decision`.

- The fleet is synthetic: real DTU photos of one Nordtank turbine grouped into 12 turbines for the demo — impact: rankings illustrate the method, not a real farm — issue: #11
- Sizes are relative (pixels and share of blade area), not millimetres: tiles carry no scale — impact: severity relies on relative size and appearance — issue: #6
- Severity has no public reference labels; it is graded against our own illustrative rubric and checked on a small hand-labelled set (one non-specialist applying that rubric) — issue: #7, #10
- The git/gh restrictions on agents are only partly enforced: the `deny` rules in `.claude/settings.json` are prefix patterns, so flags after the branch name, `git -C <dir> push`, `--amend`, `git config user.*`, `gh api -X ...` and similar are not matched. The rest is enforced by instruction (`AGENTS.md` rule 9) and by GitHub branch protection on `main`, which only the human can configure — impact: an agent could break a rule by accident; the human merges every PR — issue: #1
- The API contract checks shapes, not cross-object invariants (summary counts vs images, unique turbine ranks, box corner order, step order); only the example fixtures are checked for consistency by a test, and fixtures are validated by pydantic, not by a JSON Schema validator — impact: the pipeline must build consistent objects itself — issue: #12
- The contract has no per-class threshold sweep, operating-point marker, error-gallery entries or severity confusion matrix in `EvalReport`, no per-defect 2017-vs-2018 comparison object and no structured tool result in `AgentStep` (text only); `WorkOrder.evidence` is free text, so the "verified assessment only" rule must be enforced in the agent's `create_work_order` tool — impact: extend the contract (minor version) when #9, #10, #11 need it — issue: #9, #10, #11
- Tiles are served from the gitignored `data/`, so the Render image must fetch or bake the demo tiles at build time, or the inspection viewer shows broken images — impact: broken images in the deployed viewer — issue: #14
- The inspection year of a tile is unknown (no tags in the YOLO derivative, `DJI_xxxx` names in the original): the 2017/2018 inspections in the demo are a synthetic grouping of real photos, and the "2017 vs 2018" comparison illustrates the method, not real degradation — issue: #4, #11
- Split groups are DJI frame numbers: if one number was used in both inspection years, both photos share a group (more conservative, never a leak) — issue: #4
- Neighbouring photos (`DJI_000N`, `DJI_000N+1`) are probably near-duplicate views of the same blade area but are grouped only by exact photo number, so near-duplicates can fall on both sides of the dev/held-out split — impact: held-out metrics may be slightly optimistic — issue: #4, #16
- The dataset download URL is a signed Dataset Ninja link that may expire; the fallback (Kaggle) needs credentials. A failed build leaves `data/heldout/` unsealed (the seal runs last), a `.part` file already at full size gets HTTP 416, and every rebuild deletes `data/dev/` — impact: none on the replay demo; re-run `poe data` and re-check the mode of `data/heldout` after a failed build — issue: #4
- Calls that fail are assumed unbilled, which is unverified: (a) an attempt or call that times out after the provider already billed it is released from the spend log as free; (b) a 2xx whose body cannot be parsed (`MetaInvalidResponseError`) is now retried once and each such attempt is settled at its worst-case estimate (#23), so the log may over-count it if the provider did not bill it, and the real billed amount of that attempt is unknown; (c) a `KeyboardInterrupt`, `SystemExit` or kill mid-request keeps the reservation counted at its estimate (the request may have been billed; the next run still sees it) — impact: the cumulative cap can be off by a few calls; compare with the provider's usage page after real runs — issue: #2
- The spend log is `.spend/spend_log.jsonl` (gitignored): deleting it, or pointing `BLADESIGHT_SPEND_LOG` elsewhere, resets the caps, and a damaged log blocks every call (fail closed) until a human repairs it — impact: manual cleanup, and dropping a line removes its spend from the total — issue: #2
- The inter-process cap lock uses `fcntl` (Linux/macOS); on Windows the cap is only enforced per process — impact: none on the dev machines and CI — issue: #2
- Rate limits: Baseten's 15 requests/minute is now enforced client-side by a sliding-window limiter (`meta/ratelimit.py`) shared by every client and thread of one process, but not across processes (two live Baseten processes at once can still exceed it and fall back to 429 backoff); Meta's 3,000 RPM per team is still handled reactively by backing off on 429 — impact: run one live Baseten process at a time — issue: #2, #15
- `meta-sam-parser` is under the SAM License (Meta): attribute it in the README and keep its licence text with any redistribution; Muse Spark box output ("perception grounding") and `POST /v1/responses/input_tokens` are not used — issue: #2
- Still unconfirmed after the real calls (`docs/evidence/meta-api-step1.md`): whether `input_tokens` includes the cached tokens (`cached_tokens` was 0 in every call), `temperature` and the tool-call item shapes on Meta Responses, `store` on SAM requests (not sent; the SAM reply echoes `store: true`, read from the live reply, see the evidence file), reasoning-effort values other than "low" and the default, Baseten's image input format, its reset-header names and its real rate limits (15 RPM / 100k TPM assumed) — impact: those paths may need small fixes in `http_provider.py`; costs are the documented prices times real usage, not checked against an invoice — issue: #2
- Muse Spark calls default to `store=false` and `reasoning.effort="low"` (both accepted: reasoning 686 to 203 tokens, cost -46% on the same prompt); the quality of grading under "low" is not evaluated and lower values were not tried — impact: re-check severity quality in #7/#10 and override with `META_REASONING_EFFORT` — issue: #2
- SAM mask and box geometry (raster exactly the box size, placed at its top-left, inclusive `x2`/`y2`) was observed on 28 masks over two photos and checked visually, but the mask tokens' `x=0;y=0` are ignored and no blade-defect image was tested; early SAM confidences (0.68-0.95 for cars and turbines, 0.52-0.79 for "rotor blade") come from two images with no reference labels — impact: not evidence for the #3 go/no-go — issue: #2, #3
- The pre-call cost estimate ignores the arguments of assistant `tool_calls` in the input (a small underestimate in multi-turn agent loops; the overshoot is bounded to one call because settlement uses the real usage) — impact: slightly low reservation estimates for the fleet agent — issue: #2, #12
- Enabling DEBUG logging for `httpx`/`httpcore` may print request headers, including the bearer token (not verified): never enable it with a live key; the client's own logs never include headers — impact: key leakage in logs — issue: #2
- A Muse Spark reply whose `usage` has `input_tokens` but no `output_tokens` is read as 0 output tokens (only an all-zero usage settles at the reservation estimate), so such a call is logged below its real cost — impact: the cumulative cap can under-count; not observed on real replies so far — issue: #2
- Only the attempt that succeeds is billed in the spend log: earlier attempts of the same call that failed with a 5xx, 429 or timeout are counted as free even if the provider billed them — impact: under-count of up to `max_retries` calls per retried call; compare with the provider's usage page — issue: #2
- `store` and `reasoning_effort` are part of the chat cache key, so replaying with a different `META_STORE` or `META_REASONING_EFFORT` than the recording run misses every cached chat (in replay mode, a `CacheMissError`) — impact: keep the production env equal to the recording env — issue: #2, #12
- `DiskCache` assumes a writable directory: on a read-only cache directory a live call is billed and settled, then `put` raises and the result is lost; a corrupt entry's `unlink` also raises instead of being a miss — impact: replay deployments must mount the cache on a writable path (or only read valid entries) — issue: #2, #14
- The spike (#3) used 14 damaged and 4 clean dev tiles (20 + 5 for the text-only run) with no confidence intervals, and one dirt truth box, so dirt detection is unmeasured; its numbers decide go/no-go only and must not be quoted as results — issue: #3, #9
- Truth boxes are small (73% under 400 px^2 in the spike sample), so box-level recall at IoU 0.3/0.5 is low for any detector; results are reported at image level and with a lenient overlap too — impact: headline detection numbers will look modest next to a trained YOLO — issue: #9
- `wind turbine blade` found no blade on 586x371 close-up tiles (0/5), so blade-relative measures and the blade-context filter of #6 cannot rely on that concept — impact: position along the blade may be unknown for many tiles — issue: #6
- Mask outlines for the UI are one left/right span per row (holes and separate parts in one row are filled): approximate, for drawing only; measurements use the mask — impact: slightly generous overlays on thin or split defects — issue: #5
- Measurements are relative (pixels, shares of the tile or blade), never millimetres; the tile carries no scale and no camera distance — impact: severity rests on relative size and appearance, and sizes are not comparable across photos taken from different distances — issue: #6
- Position along the blade needs a blade mask, and the blade concept found none on 10 of 10 close-up tiles: most defects will report `position: unknown` and `blade_area_ratio: null` (the share of the tile is always given); when a blade is found, the root is guessed as the wider end of its principal axis and a tile may show only a part of the blade — impact: root/mid/tip is a heuristic on the visible segment, not on the whole blade — issue: #6
- Elongation (1 - width/length from the mask's principal axis) separates cracks from patches only roughly; thin diagonal masks are measured in pixels of a 586x371 tile — issue: #6
- A detection run costs about 0.014 USD per tile, budgeted at 0.015 (4.5 USD for 300 tiles) and needs the cumulative `META_SPEND_LIMIT_USD` raised above the 0.50 default; the public demo replays cached results only — issue: #5, #9, #14
- The detection cache lives in the gitignored `.cache/`, so the deployed replay demo needs its own cache built with the current request keys; overlapping masks of different labels (damage and dirt on one region) are never merged, and merging is greedy and single-pass — issue: #5, #14
- `poe detect` is a dev tool: a bad tile id or missing file ends in a traceback, and its held-out guard only checks the path for `heldout` — issue: #5

- The blade root is guessed as the wider end of its principal axis (ties and bent or partial blades can flip it), a defect less than half inside the blade gets no position, `blade_area_ratio` can exceed 1 when the blade mask is a small fragment, and blade and defect masks are assumed to share the tile's size — issue: #6
- Severity was first graded on only 10 dev defects (none above 3) with a first-pass review by the agent, not a person; agreement with a human was measured later on 40 other crops (#10, kappa 0.12, `docs/evidence/severity_agreement.md`): the rubric's serious end is untested and the grades are not a measured accuracy — issue: #7, #10
- Tiny defects were graded from a close crop that enlarged a few pixels and read as unreadable (confidence 0.15-0.35); since the farm run the crops are undistorted squares with a larger minimum (`assess/crops.py`), but severity agreement with the human labels (kappa 0.12) was measured on the older crops and not repeated — issue: #7, #10
- Verification thresholds (0.30 / 0.15) are first guesses tuned on a 17-defect sample of the dev farm, and the second look uses the same model family as the first, so correlated mistakes agree: `ok` means the two looks agree, not that the grade is right. Shares on the dev farm: 36% `ok`, 51% `needs_review`, 13% `reinspect` (`docs/evidence/fleet_run.md`) — issue: #8, #9
- The grading CLI writes its results only at the end of a run or on error; a killed process loses the unwritten rows — issue: #7
- Detection on dev (`docs/evidence/eval_dev.md`, 300 tiles, no tuning on them beyond the spike): box-level damage recall is 0.22 at IoU 0.3 and precision 0.37 because most dataset boxes are tiny; the false-alarm rate on clean tiles is 0.21; dirt is poor (precision 0.05, 36 boxes) and should not be presented as a detector — issue: #9
- The eval sample over-samples labeled tiles (two thirds), so per-image false-alarm rates are higher-prevalence than a real inspection; precision and recall are per box, the clean-tile false-alarm rate is reported on its own — issue: #9
- The severity gold set measures agreement with `docs/rubric.md` applied by one person with no wind-energy experience (blind to the model on these crops, but the author of the rubric who had seen earlier model gradings), not severity validated by a wind-turbine specialist; there is no second rater, so the ceiling for agreement is unknown; the 40 crops are dataset boxes chosen by size quartile (large boxes over-represented), the model also sees measurements that the human does not, and n = 40 gives a wide interval. Measured: quadratic weighted kappa 0.12 (95% interval -0.05 to 0.29), the model grades 1 on 29 of 40 crops (`docs/evidence/severity_agreement.md`), on the crops as the labeller saw them (stretched squares, frozen in `gold.py`); the undistorted square crops introduced later for the farm run (PR for #11) were not re-measured against these labels — issue: #10, #7
- Bootstrap intervals resample tiles, but tiles of one source photo are correlated, so they are probably too narrow; a cache-only re-run of `poe eval` records 0 USD (cache hits are free), so the real cost of a run is the live run's, taken from the spend log — issue: #9, #16
- Agreement compares severity only: the second look's defect type is not stored or compared, so crack vs dirt at the same severity counts as full agreement — issue: #8
- The Docker build streams the 2.8 GB dataset archive to extract the demo tiles (the build time depends on the source's speed: 2.8 GB at the 4 MB/s measured for the original download is about 12 minutes worst case, the local `docker build` was slower because of the steps around it; the Render build time is not measured; on Nov 4 the same host gave this machine 0.36 MB/s and a clean clone timed out after 3 hours with 12 of 96 tiles, `docs/evidence/clean_clone.md`); the build is strict, so if that source is slow or down a deploy fails or takes long and the previous deploy stays live: any change to `README.md`, `src/`, `replay/` or `docs/evidence/` can then not reach the public demo until the host recovers — issue: #14
- The fleet is synthetic and small: 24 inspections of 4 tiles each from one turbine's photos, at most 4 detections graded per tile; 55 of the 96 tiles had no detection; no defect was graded above severity 3, so the demo has no P1 repair and its top-ranked turbines are `needs_review`; the agent's ranking is the deterministic score, not a judgement — issue: #11
- Verification thresholds (0.30 / 0.15) were chosen on the first 17 defects of this same farm, so the 36% / 51% / 13% split of verdicts is not an out-of-sample estimate; on the first, stricter thresholds (0.5 / 0.25) only 1 of 17 defects was `ok` — issue: #8, #11
- The agent saw only the stored results, and one run per model is stored (`run-final` on Muse Spark, `run-open-weights` on Muse Spark Open); a different run of the same model could rank the same turbines but write different orders (the ranking and the evidence rule are code, the wording is the model's) — issue: #11, #15
- Effect of the threshold change on the first farm run (v1 detections, before #22): with the original thresholds (0.5 / 0.25) 12 of the 96 defects would be `ok` instead of 33, and 2 of the 3 repair orders (WO-001 d2 and d7, WO-003 d6 depend on a combined confidence between 0.30 and 0.50) rest on the lowered threshold; `ok` means "the two looks agree and combined confidence is at least 0.30", not a validated severity (kappa 0.12 against the human labels, `docs/evidence/severity_agreement.md`). The "mean 0.38" and "1 of 17" of the first sample can be recomputed from `replay/inspections/` T01-2017, T01-2018 and T02-2017 — issue: #8, #11
- Ranking ties: ranks 4-5 tie at 4.0, ranks 6-8 at 0.25 and ranks 9-12 at 0.0, ties are broken by turbine id, T04 ranks with no verified defect, a turbine with 2 verified severity-3 defects shows status `needs_review` because pending defects outrank `attention`, and "worse" for T03 means two verified severity-1 defects against none on a synthetic grouping — issue: #11
- `write_report` checks only complete defect ids and `WO-nnn` ids against the stored results (partial ids and numeric claims are not validated), the agent's priority is not coupled to severity in code, and every run overwrites `replay/work_orders.json` and `reports/latest.json` (a stub or failed run too) — issue: #11
- Detection evaluation caveats (`docs/evidence/eval_dev.md`): the 300-tile sample over-represents tiles with boxes (about two thirds against about 22% of the split), so box precision (0.37) and the false alarms per image (0.19 at score 0.7, 0.79 unfiltered) are optimistic for a real inspection; "image-level recall" (0.767) is per 586x371 tile and location-free (any damage prediction on a damaged tile counts, a detector firing on every tile would score 1.0), so it must be quoted with the 21% false-alarm rate on tiles with no dataset box, and "clean" only means no dataset box (the dataset labels may be incomplete, so some false alarms may be real damage); the pipeline was chosen on an 18-tile dev spike and no other tuning used the 300 tiles (the spike tiles can fall inside the sample); the run's 1,093 live calls and 3.1759 USD come from the spend log (`.spend/`, not committed) — issue: #9
- The dev bootstrap intervals in `docs/evidence/eval_dev.md` (damage precision 0.311-0.424, recall 0.180-0.264) were computed with the earlier unstratified bootstrap; re-rendering from the cache now uses the stratified one and gives slightly different bounds (point estimates are unchanged) — issue: #9, #16
- The API reads its JSON on every request: a corrupt file in `replay/`, `docs/evidence/eval_dev.json` or `eval_heldout.json` answers 500, `POST /api/runs` (live mode, admin key) is a synchronous 1 USD agent run with no lock (the cumulative spend cap still bounds the total) and is the first thing to cut, and the default paths are relative to the working directory (set `BLADESIGHT_*_DIR` or run from the repo root; `web/dist` must exist before the process starts) — issue: #12, #14
